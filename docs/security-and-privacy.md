# 보안·개인정보 설계

## 접근 제어 (D1에는 RLS가 없으므로 Worker에서 강제)

- 모든 개인 데이터 쿼리는 세션 사용자 ID 조건(`WHERE user_id = ?`)을 포함합니다. 다른 사용자의 행 ID로 수정·삭제를 시도하면 404가 됩니다.
- 동반자 데이터는 `GET /api/shared/:ownerId` 하나로만 제공되며, 매 요청마다 `shares` 행을 다시 확인합니다. 허용되지 않은 항목은 조회 자체를 하지 않습니다(`worker/routes/sharing.ts`의 `buildSharedView`).
- 동반자를 위한 쓰기 API는 존재하지 않습니다.
- 공유 해제 = `shares` 행 삭제. 다음 요청부터 403이며, 실시간 소켓은 Durable Object에서 즉시 닫힙니다(코드 4403).
- 실시간 채널은 데이터를 보내지 않고 "바뀐 주제"만 알립니다. 동반자 소켓에는 권한이 있는 주제만 전달됩니다.
- 위 규칙은 `tests/worker/*.test.ts`에서 실제 Workers 런타임으로 검증합니다.

## 인증

- 비밀번호: PBKDF2-SHA256(100,000회, 16바이트 솔트). 평문·가역 저장 없음.
- 세션: 무작위 32바이트 토큰을 HttpOnly·SameSite=Lax·Secure 쿠키로 전달, DB에는 SHA-256 해시만 저장. 30일 만료.
- 로그인 실패 15분 10회 초과 시 제한.
- CSRF: 상태 변경 요청은 같은 출처 `Origin`과 JSON 본문만 허용.

## 초대 링크

- 무작위 32바이트 토큰, DB에는 해시만 저장. 72시간 만료, 1회 사용, 취소 가능.
- 비로그인 미리보기는 유효 여부만 알려주며 초대자 이름도 노출하지 않습니다.

## 개인정보 최소화

- 수집: 이메일, 표시 이름, 시간대, 사용자가 직접 입력한 약물·식사 기록.
- 로그: 오류 이름·메시지만 기록하며 요청 본문·사용자 데이터는 남기지 않습니다.
- 비밀 키: 클라이언트 번들에 비밀 값이 없습니다(세션은 서버 측 쿠키). 외부 서비스 키도 사용하지 않습니다.
- 회원 탈퇴: 비밀번호 확인 후 `users` 삭제 → 모든 개인 테이블 `ON DELETE CASCADE`.
- 기본값: 초대 시 식사 컨디션만 공유가 켜져 있고, 약물·반응 공유는 사용자가 직접 켜야 합니다.

## 출시 전 검토 필요 사항

- 약물 복용 정보는 개인정보보호법상 민감정보(건강)에 해당할 수 있어 별도 동의·처리방침 보완이 필요할 수 있습니다.
- 서비스 문구가 의료기기(소프트웨어)·의료 광고 규제에 해당하지 않는지 확인이 필요합니다.
- 비밀번호 재설정·이메일 인증은 이메일 발송 수단이 필요해 MVP에 포함되지 않았습니다.
